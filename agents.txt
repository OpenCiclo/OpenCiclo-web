# agents.txt — OpenCiclo / Ciclo

Machine-oriented map of this repository. Humans should start at README.md, /help, and CONTRIBUTING.md.
Do not treat this file as user-facing copy. Do not paste it into the UI.

Live copy on a hosted app: GET /agents.txt (apps/web/public/agents.txt).
Cursor: also see the short AGENTS.md at the repo root. Do not edit apps/web/AGENTS.md; Next.js regenerates it.

## Product split

- OpenCiclo: Python forecasting library at repo root (`openciclo/`). Local-first. No accounts, sockets, or telemetry in the package.
- Ciclo: optional Next.js web app in `apps/web/`. Encrypted diary + TypeScript port of the released forecast path.
- Ciclo for Android: Capacitor shell in `apps/mobile/` around a static export of `apps/web`. Same UI, crypto, forecast, and vault code. See "Android app" below and `docs/android.md`.
- Names: Python import is `openciclo`, never `oddy`. Some crypto labels and legacy cookies still say `oddy-*` / `oddy_session` — do not rename those without a migration.
- Public name in the UI: Ciclo. Repo/docs: OpenCiclo.
- Brand: the names OpenCiclo and Ciclo and the round-sea logo are trademarks, outside Apache-2.0 (TRADEMARKS.md). The logo files listed there (`lib/brand/sea-mark.ts`, the generated icons, `docs/brand/sea-mark-motion.html`) are all rights reserved: keep their notices, never mark them Apache-2.0, and add any new logo file to the list.

## Non-negotiables

- Not a medical device. Forecasts can be wrong. Not contraception, not a fertility/ovulation test, not pregnancy detection.
- User-facing copy that discusses cycles must keep that disclaimer (see `apps/web/lib/i18n.ts` `disclaimer`).
- No Clerk, Auth0, analytics SDKs, ad pixels, or exception trackers that could receive health fields.
- No neural nets / transformers / deep learning.
- Do not log period dates, mnemonics, passwords, AES keys, or plaintext diary.
- Do not add `user_id` / `account_id` / `pubkey_hash` to `research_contributions`. A join table account→pool_id is a de-anonymization bug.
- The population prior in `openciclo/artifacts/released_model.json` comes from published aggregates only (`LITERATURE_PRIOR_*` in `openciclo/constants.py`, cited there and in MODEL_CARD.md). No local dataset's rows enter the artifact: mcPHASES may choose hyperparameters (k, length family) and its aggregate selection metrics are recorded, Utah/Creighton and Kaggle never. `--fit-release` refuses a fitted prior and a length family whose shape would be fitted on data (log-normal, empirical).
- Estimated ovulation uses a published luteal-phase distribution only (`LUTEAL_*` in `openciclo/constants.py` and `apps/web/lib/forecast/constants.ts`: Bull et al. 2019, Table 1). mcPHASES LH data only score it (`python -m openciclo.evaluation.ovulation`, aggregates only). Wording: "estimated ovulation", "may fall", always with "does not confirm ovulation / is not contraception"; never "safe days", "infertile days", or a chance of pregnancy per day.
- Do not commit restricted CSVs (mcPHASES, Creighton, etc.). Gitignored under `training/dataset-do-not-commit/`.
- Do not invent metrics. Do not choose `model_id` from synthetic CI scores.
- English for code, comments, and documentation. Help pages: English only.
- UI languages (`LOCALES` in `lib/i18n.ts`): es, en, pt-BR, fr, de, it, nl, pl, ca, ca-valencia, eu, gl. Spanish and English live in `i18n.ts` (`Messages` is `typeof en`), `lib/marketing/copy.ts` (landing) and `lib/mail-copy.ts` (code email); the app texts and the mail ship with every page, the landing copy only with the public site (`marketingCopy` in `lib/marketing/locale.ts`; never import it from an app screen). Each other language is one file, `lib/locales/<tag>.ts` (a `LocaleModule`: messages + marketing + mail), loaded on first use by `lib/locales/registry.ts`; read text through `useCiclo().t`, `messagesFor`, `marketingCopy` or `mailCopy`, never `messages[locale]`. A new UI string goes into `es`, `en` and every locale file in the same change; `lib/locales/locales.test.ts` fails on a missing key, an empty string, a changed `{placeholder}`, or a landing `href`/`icon`/`key` that differs from English. Translations are machine-assisted until a native speaker reviews them, health copy and the disclaimer first. Valencian (`ca-valencia`) is the AVL standard, written as changes on top of Catalan. Copy that exists only in ES/EN (Learn articles, the operator console, the season guide) uses `contentLocale`: Spanish for ca, ca-valencia, eu, gl; English otherwise. Dates go through `Intl` with the locale tag itself. App versions before this change read any saved diary locale other than `en` as `es`. The first screen's language is the one saved on this device (`ciclo.locale`), else the first of `navigator.languages` Ciclo speaks, region or variant dropped (`pt-PT` → `pt-BR`, `ca-ES-valencia` → `ca-valencia`), English when none (`initialLocale` / `matchLocale` in `lib/client/initial-locale.ts`; the same matching as ES5 source runs in the Android layout's boot script and the WebView update page, which also prefers a saved `ciclo.locale`). A diary that opens brings its own language. Texts that say "browser" have an Android wording: key `<name>Android`, right after the web key in every language file, listed in `lib/locales/android-copy.ts`; `messagesFor` swaps them in the Android build, so screens read the plain key.
- Documentation voice for humans: short sentences, define jargon once, no marketing filler. This file is exempt.

## Docs surfaces (do not mix)

- `/learn` — health education in 14 categories (cycle, periods, symptoms, conditions, intimate health, fertility, contraception, pregnancy, sexual health, menopause, mind, lifestyle, puberty, care). Bilingual target: `en` is required, `es` is optional until translated. A UI language with no copy for an article shows it in Spanish or English (`articleCopyLocale`: Spanish for ca, ca-valencia, eu, gl when it exists) with an "English only for now" / "Spanish only for now" badge. Each article cites sources and may list `related` slugs. Shipped source: `apps/web/lib/learn/content/<category>.ts` (types and helpers in `lib/learn/articles.ts`). Operator CMS: `learn_articles` in Postgres, merged in `lib/learn/catalog.ts` (DB row wins; draft hides shipped). Do not dump hosting/crypto here.
- Learn delivery: lists (the index, the landing, related links) get `LearnArticleSummary` (slug, category, date, title, summary), never whole articles. The index overlay loads the body when an article opens (`loadLearnArticle`, `lib/learn/bodies.ts`): the web from `/learn/<slug>/article.json` (merged with `learn_articles`), Android from that category's chunk of `LEARN_ARTICLES`. Never import `lib/learn/content` statically into client code: it is about 750 KB.
- The landing, `/learn`, every `/learn/[slug]` page and its `article.json` are static (ISR, `revalidate = 3600`). They read `learn_articles` through `unstable_cache` tagged `learn` (`LEARN_CACHE_TAG`, `lib/learn/load.ts`; refreshed at least hourly) and inherit the tag. Saving or deleting an article in the console calls `revalidateTag("learn", "max")` (`lib/server/learn-articles.ts`): stale-while-revalidate, never `revalidatePath` or a tag without a profile (those expire the pages, and an expired page whose regeneration fails is a 500). A visit after a save is served the old page and regenerates it; that regeneration waits for fresh rows, and if the database fails Next hands back the last cached rows, so the page keeps its last good content. `loadPublishedLearnArticles` throws only when no rows were ever cached and the database fails; the landing (featured articles) and the sitemap then fall back to the shipped library (`shippedLearnArticles`), Learn pages keep their previous version. Unknown or malformed slugs (`isLearnSlugParam`: pattern, at most 120 characters) are a real 404 (`notFound()`), before any read.
- Builds read `learn_articles` too (one query per build worker) and fail when it cannot be read: prerendering the shipped library would show articles the operator hid. With no `DATABASE_URL` (Docker, CI) a build uses the shipped library. Emergency switch: `LEARN_BUILD_WITHOUT_DB=1` (build phase only) builds with the shipped library and a loud warning, to ship a fix while the database is down; unset it afterwards (Help "Host on Vercel").
- A console save made while a deploy is building (the new build may have read the table before the save), or from a preview deployment's console (it marks the preview's cache, not production's), reaches production only at the next hourly refresh: after a deploy, save the article again in production's console if it must show at once.
- `/help` — product/operator docs (hosting, encryption, UI labels, forecast behaviour). English. Source: `apps/web/content/help/*.md` + catalog `apps/web/lib/help/articles.ts`. Public, no wallet.
- `/privacy` — the privacy policy (Google Play and GDPR art. 13). Source: `lib/privacy/policy.ts`, Spanish and English authoritative; other UI languages show one of them through `contentLocale` with the `learnSpanishOnly`/`learnEnglishOnly` badge. Needs legal review before launch. Summary for the repo: `PRIVACY.md`. Contributor checklist: `docs/privacy.md`. Launch checklist (data map, processors, DPIA outline): `docs/play/privacy-checklist.md`; store listing draft: `docs/play/listing.md`. When what the app stores, sends or keeps changes, update the policy (and `PRIVACY_POLICY_UPDATED`), `PRIVACY.md` and the checklist together; `lib/privacy/policy.test.ts` lists every table, and every column of the tables holding personal data, and fails on a new one. `?lang=<tag>` on `/privacy` and `/delete-account` picks the text's language for display only (`legalLanguage`, `components/legal-page.tsx`; never saved); the store listing links `?lang=en` / `?lang=es`. The policy must describe what the app does today, for example that every sign-up keeps the person signed in (`persist: true` in onboarding). The owner's details live in `lib/marketing/copy.ts` only: `CONTROLLER`, `PRIVACY_EMAIL`; while one is null the pages leave its sentence out (never a placeholder or an empty mailto). The server region comes from `apps/web/vercel.json` (`lib/privacy/hosting.ts`; a region without a place name fails `hosting.test.ts`).
- `/delete-account` — web only (no `.android.tsx` twin), the public page Google Play asks for: how to delete an account and its data without the app. Source: `lib/privacy/delete-account.ts` (ES/EN, like `/privacy`). The request by email for lost credentials shows only once `PRIVACY_EMAIL` is set. Links from these documents to web-only pages open the website in the Android app (`WEB_ONLY_PATHS`, `resolveLegalHref`).
- `/licenses` — third-party notices, web and Android, prerendered at build time from `package-lock.json` + `node_modules` (production, non-optional packages; `lib/licenses/collect.ts`), the OFL fonts (`lib/licenses/ofl-1.1.txt`), and in the Android build `apps/mobile`'s packages and the Maven libraries inside the app (`lib/licenses/android-maven.ts`: a reviewed static list with versions, holders and the Cordova NOTICE; its header says how to regenerate it from `gradlew :app:dependencies --configuration releaseRuntimeClasspath`, and `android-maven.test.ts` fails when `variables.gradle` or `app/build.gradle` versions drift from it). A release export (https `CICLO_API_BASE`) fails when an `apps/mobile` lockfile package is not installed; a development export warns. Linked from `/privacy`. Settings opens the same list in a sheet (`LicensesList`, `components/licenses-view.tsx`) from `/licenses.json`, a static route built with the app (`app/licenses.json/route.ts`, Android twin `route.android.tsx`; both call `buildLicenseReport`, `lib/licenses/report.ts`).
- Sign-up consent: the first onboarding step shows what is stored and where (`signupConsent*`) and keeps the three ways to create a diary disabled until "I agree" is ticked (`signupConsentRequired` says why). The policy opens over the screen (`components/policy-dialog.tsx`), so the tick survives reading it. ## Hosting

- Intended production: Vercel project root directory `apps/web` + Neon Postgres.
- Installs are `npm ci` everywhere: CI, the Dockerfile, and Vercel (`apps/web/vercel.json` `installCommand`). Keep `package.json` and `package-lock.json` in sync or every build fails. CI also runs `npm audit signatures`. `@noble/ed25519`, `@noble/hashes` and `@scure/bip39` are pinned to exact versions (no `^`): upgrade them in their own commit, a week or so after a release, and review their lockfile diff (docs/threat-model.md "Hardening backlog"). The other runtime packages that reach the client bundle (`jsqr`, `uqr`, `@zonneplan/suncalc`, `lucide-react`) are pinned exactly too.
- Functions run in `fra1` (`apps/web/vercel.json` `regions`), next to the Neon database in Frankfurt; keep them in the database's region.
- Public files: `public/robots.txt` (crawl the public site; not `/api/`, `/console`, `/dev-*`; advertises `https://www.openciclo.com/sitemap.xml`, `PRODUCTION_SITE_ORIGIN`), `app/sitemap.ts` (public pages, Learn and Help articles; URLs on `SITE_URL` if set, else the origin the sitemap was requested on, never production's apex `APP_URL`; shipped slugs if the catalog cannot be read), `public/.well-known/security.txt` (RFC 9116; renew `Expires` before it lapses, `lib/sitemap-entries.test.ts` fails 30 days ahead). The web service worker (`public/sw.js`) has no fetch handler; keep it that way unless offline support is designed (never cache diary, vault, or recovery responses).
- Env: `DATABASE_URL`, `SESSION_SECRET`, `EMAIL_LOOKUP_SECRET`, `APP_URL` (no trailing slash). Email signup needs `RESEND_API_KEY` + `MAIL_FROM` (production) or SMTP (local Mailpit). If neither is set, email signup is 503. Optional `CONSOLE_EMAILS` (comma-separated). If unset, `/console` is 404. Optional `MIN_ANDROID_VERSION_CODE`: API routes answer 426 to Android builds below it (see "Android app"); leave it unset until older builds no longer matter. Optional `SITE_URL` (canonical origin for sitemap URLs) and `LEARN_BUILD_WITHOUT_DB=1` (emergency builds only, see Learn delivery). Day-to-day email sign-in does not use inbox magic links; signup sends a 6-digit code once.
- SQL: `apps/web/drizzle/0000_init.sql`, `0001_pool_upsert.sql`, `0002_learn_articles.sql`, `0003_mailbox_pending.sql`, `0004_account_activity.sql`, `0005_vault_version.sql`, `0006_rate_limit_hits.sql`, `0007_lookup_indexes.sql`, `0008_friends.sql`, `0009_feedback.sql`. No plaintext health columns. Never store plaintext email — HMAC `email_lookup` only; the one exception is `feedback.contact_email` (below). `0004` is one row per account per UTC day, written after the response on sign-in and on `GET /api/vault` (the app's start); the console shows counts only, and those rows are never pruned. `0007` only adds indexes (`recovery_mailboxes(account_id)`, `account_activity_days(day)`); no code may depend on an index existing. `0008` adds `friend_books` and `friend_boxes` (see "Friends"). `0009` adds `feedback` (see "Feedback").
- Postgres connection (`lib/db/index.ts`): TLS verify-full by default; plain only for local hosts (`localhost`, `127.0.0.1`, `::1`, the docker `db` service) or `DATABASE_SSL=disable`; `DATABASE_SSL=require` keeps TLS without the certificate check. The URL's `sslmode` is ignored. Pool per instance: `max` 3, `idle_timeout` 240 s, `connect_timeout` 10 s. A missing `DATABASE_URL` or secret throws `ConfigError` (`lib/server/env.ts`), logged as e.g. `ConfigError SESSION_SECRET_MISSING`.
- Database tests use `lib/db/test-db.ts`: they skip without `DATABASE_URL` and refuse (fail on import) a URL whose host is not in `LOCAL_DATABASE_HOSTS`, so no test can write to a remote database. CI's web job runs them against a Postgres 16 service with every `drizzle/*.sql` applied in order.
- Production has real users. Migrations are hand-written SQL, additive, idempotent (`IF NOT EXISTS`), numbered with no gaps, applied with `psql -v ON_ERROR_STOP=1 -1 -f` after a Neon snapshot. `lib/db/migrations.test.ts` rejects DROP/TRUNCATE/DELETE/UPDATE/RENAME/ALTER COLUMN unless listed in `REVIEWED`, and checks every file is listed in docker-compose.yml, README.md, and the two hosting Help pages.
- Never use `drizzle-kit push` (removed from the repo). `lib/db/schema.ts` mirrors the SQL, including the partial unique index on `research_contributions.contributor_key_hash`; `schema-drift.test.ts` fails on any mismatch. Upserts on a partial index need `targetWhere` with the same predicate.
- Local UI: `cd apps/web && npm run dev` with `.env.local` from `.env.template`. You cannot see or edit `.env`.
- Local stack: `docker compose up --build` from repo root, after writing `SESSION_SECRET` and `EMAIL_LOOKUP_SECRET` to a root `.env` (command at the top of docker-compose.yml; the web container refuses to start without them). `docker compose up -d db mailpit` needs no `.env`. An install upgraded from the old compose file must put the values it used to hard-code in `.env` (README "Self-host"): a new `EMAIL_LOOKUP_SECRET` breaks every existing mailbox lookup. `APP_URL` is `http://localhost:3000`. Every port binds to `127.0.0.1`. No secrets in docker-compose.yml or the image; `apps/web/.dockerignore` keeps `.env*` out of the build context; the runner is the unprivileged `node` user. Self-hosters serving others need a reverse proxy that sets `X-Forwarded-For` (the rate limits read it).
- Do not document or reintroduce Tailscale / serve tunnels. Public access is Vercel.
- Docker image copies `content/` into the runner so `/help` can `readFileSync` markdown (also `outputFileTracingIncludes` in `next.config.ts`).
- `/dev-seasons` is a playground; `notFound()` in production. Hide the tab bar and the desktop header on `/dev-*`, `/help`, `/contact`, and `/console` (`hidesAppChrome` in `lib/client/app-chrome.ts`).
- Next CSP: relax `unsafe-eval` + `ws:` only when `NODE_ENV !== production`. `script-src` keeps `'unsafe-inline'` in production too: the App Router inlines its flight data as scripts and the root layouts inline the theme and splash boot scripts. Nonces would make every page dynamic and cannot work in the static Android export, so do not remove it without a plan for both (docs/threat-model.md, XSS row). Other headers (`next.config.ts`): `Permissions-Policy` allows only `camera=(self)` (phrase QR scanner); `Strict-Transport-Security: max-age=63072000` in production, without `includeSubDomains`/`preload`; `Cache-Control: no-store` on `/api/*`.

## Python library map

```
openciclo.schemas          Pydantic models
openciclo.data             cycle math, validation, synthetic, mcPHASES/Creighton loaders
openciclo.features         recency weights, length summaries
openciclo.models           baselines, shrinkage, population prior
openciclo.artifacts        released_model.json (literature prior + hyperparameters; no microdata)
openciclo.forecasting      public predict(); ovulation.py: estimated ovulation = next start − luteal phase (most likely day + shortest 80% window)
openciclo.explanations     drivers (contributed to prediction, not causation)
openciclo.evaluation       walk-forward; CI synthetic; mcphases --fit-release (literature prior); by-history breakdown; v0.reference.* never selected; ovulation (LH-dated mcPHASES cycles)
openciclo.calibration      reliability summaries
openciclo.pregnancy        due date, gestational age, trimester, term (twin of apps/web/lib/pregnancy/dating.ts); predict(excluded_starts=…) leaves out intervals that held a pregnancy
```

Public API: `from openciclo import predict`. Docs: `docs/api.md`.
Parity vectors: `python scripts/generate_forecast_parity.py` → `tests/fixtures/forecast_parity.json`.
Tests: `pytest`, `ruff`, `mypy openciclo`.

Walk-forward: only starts before s_k may forecast s_k. Never shuffle a person’s cycles into random train/test.

Shrinkage (released default): mix personal median with population prior; k from the release artifact (2.5 since engine 0.3.0; the web port reads it from its copy of the JSON; discrete Laplace 1–90). Cold start (0–1 starts) → prior, high uncertainty.

V1 predicts next period start and cycle length; estimated ovulation is derived from that forecast and the luteal distribution (docs/modeling.md "Estimated ovulation"). Optional observations are ignored by V0 predictors.

Diary schema currently v8: period starts, daily flow/mucus/symptoms/notes, forecastingEnabled, pregnancies (see "Pregnancy"); v8 added the Pregnancy symptom group. Migrations in parseDiary. New fields go in the encrypted blob, not new Postgres health columns.

Old builds and newer diaries: an Android build from Google Play stays in use for months and can open a diary saved by a newer build (the web, or a newer app on another phone). It must never save it back without what it does not know. So: bump `DIARY_SCHEMA_VERSION` (`lib/diary.ts`) for any new field or any new value in a list the diary stores (flow, mucus, built-in symptoms, symptom values, custom symptom categories, `LOCALES`); `lib/diary-schema.test.ts` holds what each version can hold and fails until you bump and add an entry. `parseDiary` throws `NewerDiaryError` for a higher version, so no merge, save, or import can turn a newer diary into a known one; `parseNewerDiaryForDisplay` reads it for showing only and labels it with this build's version. The client then opens it read-only (`updateRequiredBackend`, context `updateRequired`, `UpdateNotice`), on load and on a 409 whose blob is newer. The host is the backstop: `writeVault` never lands a save whose `schemaVersion` is lower than the stored one (it answers 409 with the current blob). Importing a file from a newer build is refused (`importNewerFile`): JSON by its `schemaVersion`, CSV by its `schemaVersion` column (first row; files from before the column existed still import). While a newer diary is open, the JSON export writes its decrypted text unchanged (`exportDiaryJson`, context `diaryNewer`) and CSV export is off, so a backup never drops what this build cannot read. `diary-schema.test.ts` also pins a hash of the code between `diary-format:begin` and `diary-format:end` in `lib/diary.ts` (what a stored diary keeps when read): change it and decide whether the version must go up (the test's header says how).

Phase heuristic (`phaseAtDate` / `cycleOverview`): flow today → menstrual observed; else calendar windows from last start + expected bleed length + an ovulation window counted back from the next start with the luteal spread (`knownCycleOvulation`: the shortest 80% of next start − 12.4 ± 2.4 days, about 15–10 days before it, never on an expected bleeding day nor on or after the next start). `cycleTimeline` and a friend's card use the same window, so the sharer's card and the friend's agree; do not feed them the open cycle's wider window without a payload change. If forecastingEnabled is false, do not show estimated follicular/ovulation/luteal.

Estimated ovulation on the calendar (`cycleOverview().ovulation`, `estimatedOvulationDates`): the open cycle's window comes from the forecast's full cycle-length distribution, so it widens with little history or irregular cycles (median 11 days; about 84% of LH-dated ovulations in mcPHASES fell inside), ends before the expected start, and its most likely day gets the stronger mark; closed cycles use the known-length window. The expanded phase card shows it as "Estimated ovulation: most likely … · window …", with a note from `WIDE_OVULATION_WINDOW_DAYS` (15) on. ## Crypto / identity (do not “simplify”)

- Device generates BIP39 12-word mnemonic.
- HKDF-SHA-256 info labels are `oddy-aes-v1` and `oddy-sign-v1` in `wallet.ts`. Changing them breaks existing vaults.
- AES-256-GCM for diary. Ed25519 for login challenge signatures.
- Email path: password wraps mnemonic (PBKDF2-SHA-256 + AES-GCM). New kits use `PBKDF2_ITERATIONS` (600k); `unwrapMnemonic` uses the count stored in the kit's `wrapParams`, only within `MIN_KIT_ITERATIONS`–`MAX_KIT_ITERATIONS` (100k–3M) and only for `pbkdf2-sha256`/`SHA-256` (`UnsupportedKitError` otherwise), so the cost can rise later without breaking installed builds. The decoy kit uses `PBKDF2_ITERATIONS` too. Before raising `PBKDF2_ITERATIONS`, plan for the decoys: kits stored at the old count would then reveal a real account (a decoy always shows the current count), so re-wrap old kits at sign-in or make decoys pick a count the way real kits are spread. A kit outside the accepted parameters asks for an app update (`UnsupportedKitError` → `UpdateRequiredError`), never "wrong password". Server stores HMAC(email) + wrapped kit only after a 6-digit inbox code (`mailbox_pending` then `recovery_mailboxes.verified_at`). Plaintext email is never a Postgres column. `POST /api/recovery/fetch` returns ciphertext only for verified mailboxes. Server must never unwrap.
- A signed-in hosted account with no email sign-in (phrase-only, or moved back from an on-device diary, which deleted the old mailbox) can add one in Settings (`AddEmailSignIn`, `addEmailSignIn` in `ciclo-context.tsx`): wrap the mnemonic with the new password, `POST /api/recovery/register` (code mail), `POST /api/recovery/confirm`, then save the local kit and set `recoveryEmailSet`. Same server path and same rules as the email sign-up; the code is always required for a new address. Settings shows **Change password** or **Add email and password** from `diary.recoveryEmailSet` alone, never from the last email typed on the device (it outlives sign-out and other accounts).
- Only `/api/recovery/register` sends mail, so only it checks the address shape: `parseMailboxEmail` (`lib/server/mailbox.ts`) keeps the HMAC normalization (trim, lowercase) and rejects whitespace, control characters, comments, angle brackets, quotes, groups, lists, and anything over 254 characters with a 400 before any lookup. Do not add that check to `/api/recovery/fetch`: a mailbox registered before it existed would be locked out.
- Never reveal whether an email has an account. `/api/recovery/fetch` answers unknown and unverified emails with a decoy kit (`lib/server/recovery-decoy.ts`: deterministic per email, same fields, sizes, and `wrapParams` key order as a real kit read from jsonb); never return 404. `/api/recovery/register` treats "taken by another account" like a new email: same 429 accounting (every limit is taken before it branches), the same writes (`startPendingMailbox`: drop the account's and the address's pending rows, insert a pending row; for a taken address its code is random and never sent, so `/api/recovery/confirm` afterwards behaves the same: `lib/server/mailbox-store.test.ts`), `{ pending: true }`, and `MAILBOX_PENDING_MIN_RESPONSE_MS` floor; the code mail goes out in `after()`, and a failed send is logged by error name/code only (never the address or the code). Confirm claims one attempt in a single `UPDATE … attempt_count < 5 … RETURNING` before comparing, so parallel guesses each use one up. Client errors stay generic ("wrong email or password") for every answer about the email; only 429 has its own message. A network failure or a 5xx is not about the email and says so (`signInUnreachable`). Do not use `recovery_tokens` (that would look like a password reset).
- Kits cached on the device (`ciclo.kits`, `lib/client/kit-store.ts`): `openKit` tries the cached kit, and when it does not open (password changed on another device) fetches the host's kit; only a host kit that does not open is `InvalidCredentialsError`. A kit is saved on the device only after the host took the sign-in or change it belongs to. Sign-out deletes `ciclo.kits` and `ciclo.lastEmail` (a cached kit can be attacked offline).
- No host-side password reset (magic link / email alone). The signup code authorizes inserting the already-wrapped kit; it does not unwrap. Changing the wrap password while unlocked is allowed: re-wrap the mnemonic (own verified mailbox, no new code); do not rotate AES or re-encrypt the diary. Lost password + lost phrase ⇒ lost hosted diary. Export/import restores data, not the old key.
- Deleting the account row cascades `recovery_mailboxes` and `mailbox_pending` (`ON DELETE CASCADE`), so that HMAC is free for someone else to verify.
- Session cookie (stateless HMAC token, 30 days, MAC compared with `timingSafeEqual`); legacy name `oddy_session` still recognized. Logout checks `Origin` when present (this host, `APP_URL`, or `https://localhost` for the Android app). Optional persist unlock goes through a `PhraseStore` (`lib/client/phrase-store.ts`): on the web it writes `ciclo.mnemonic` to localStorage, otherwise sessionStorage only; in the Android app it seals the phrase in Keystore (see "Android app"). Never call `writeStoredMnemonic` / `readUnlockState` directly from new code. Never send the mnemonic to the server.
- Only a sign-up creates an account. `/api/auth/verify` creates one only when the request brings a first diary (`ciphertext`: create account, email signup, Android move to hosted). A correctly signed key with no account and no first diary gets 404 `code: "no-account"` (`lib/auth-codes.ts`) and nothing is created: "I have an account" with a mistyped but valid phrase must never land in a new empty diary. The client throws `AccountNotFoundError`. Only the key holder can get this answer (the signature is checked first).
- Startup restore (`restoreStoredSession` in `ciclo-context.tsx`) forgets the stored mnemonic only if it is invalid. It asks `GET /api/vault` with the session cookie first and signs in (challenge + verify) only on a 401/404 or when the vault does not decrypt with the stored key (another account's cookie): `loadVaultWithSession` in `lib/client/vault-sync.ts`; the order and the cancel rules are `restoreKeptPhrase` in `lib/client/restore-session.ts`. The kept phrase blocks other sign-ins from the moment it is read until its diary opens or a confirmed Forget. If the host has not answered within `START_ANSWER_MS` (20 s), the start shows the offline copy or Try again and keeps the load going; its diary opens when it arrives, unless the start was cancelled (retries share that load). Network, server, or sign-in failures keep it and show Try again (`restoreFailed`), with automatic retries on a growing timer (`restoreRetryDelay`), on `online`, and on return to the front. Every retry runs under a `RestoreGeneration` (`lib/client/vault-sync.ts`): sign-out, Forget, creating a device diary, and any diary opened another way cancel it and stop the timer, and a cancelled run touches no state, never signs in, and never opens its diary. A kept phrase that Keystore cannot read (`UnlockStoreState.unreadable`) is treated like `restoreFailed` (`restoreUnreadable`): it blocks other sign-ins and sign-ups, Try again or Forget. A host with no account for it keeps it too and shows `restoreNoAccount` (no retry); never drop the phrase on the host's word alone. While either is shown, a kept phrase blocks every other sign-in or sign-up (`SavedSignInError`; the welcome screen hides those buttons) until the person forgets it on purpose (`forgetSavedSignIn`, after seeing it with `readSavedPhrase`). `hydrate` sets the wallet only after the vault is fetched and decrypted; never expose an unlocked wallet next to a placeholder diary, because the next save would upload it over the real vault. `ready` comes as soon as the diary is in memory; the offline copy and the pool sync run after (the pool save through the save queue). `fetchVault` throws on 401/404.
- A hosted request answered 401 while the app is open (expired cookie), or 409 `account-mismatch` (next item), signs in once with the wallet in memory and runs again (`retryAfterSignInOnce`): saves, the foreground refresh, recovery register/confirm, account delete, and the hosted → device move (a 401 there is never a refusal). It is gated on the session generation: once the session ended nothing signs in, and a sign-in whose session ended while it was out marks its cookie for clearing.
- Requests that change an account name it (C15). The session cookie is one slot that the last sign-in to land fills: an Android sign-in whose JS timed out still lands (native HTTP ignores the abort), two web tabs on two accounts share it, a late sign-in can leave its cookie for a moment after a sign-out. So `PUT /api/vault`, `DELETE /api/account`, `POST /api/recovery/register` and `POST /api/recovery/confirm` send `x-ciclo-account` (`ACCOUNT_HEADER`, `lib/auth-codes.ts`): the open wallet’s `pubkeyHash` (64 lowercase hex, the value in `accounts.pubkey_hash` and in the cookie). `requireAccount(request)` (`lib/server/account.ts`, used by those four routes and every `/api/friends` route, which also send the header) answers 409 `code: "account-mismatch"` when it names another account than the session’s, compared with the session’s hash (no extra read), before the account lookup (a cookie of a deleted account is then 409, never the 404 that DELETE counts as deleted), any rate limit, write, cookie change or mail, and the same whatever the email (S1). Without the header (older builds, tabs opened before a deploy) nothing changes; an old host ignores it, so deploy order does not matter. Client: `putVault`, `VaultBackend.save` (a device file ignores it), `deleteAccount`, `postRecoveryKit` and `confirmRecoveryCode` (`lib/client/kit-store.ts`) take the account as a required argument; `sessionRetry` hands `run` the hash of the wallet it signs in with, and `saveMerged` and `liveSessionRetry` (wipe, add email, change password) act only for the wallet whose diary is open in this session (`sessionWalletRef`, `isOpenSessionWallet` in `lib/client/vault-sync.ts`; otherwise "Locked", nothing sent, nobody signed in), so the header is always the wallet whose key sealed the diary; `lib/client/account-header-wiring.test.ts` reads that wiring from the source. A mismatch (`AccountMismatchError`, an `HttpError` 409) signs in once and retries like a 401; refused again it shows `accountMismatch` and nothing is written (the move to the device counts it as the host refusing). If the sign-in for that retry finds no account (`AccountNotFoundError`), `wipe` counts the account as already deleted, like a 404. The `GET /api/vault` calls carry no header (start, refresh, the end of an email sign-up, both moves): with another account’s cookie they read a vault this key cannot open, which fails (or signs in again at start) and writes nothing. `putVault` never reads a 409 with that code, or without a vault version, as another device’s save (merging it as an empty diary would drop every day).
- Sign-ins and sign-outs run one at a time in the order asked (`lib/client/api.ts`, one cookie slot, last Set-Cookie wins). `retryPendingLogout` is skipped while a sign-in runs, and the start's first `GET /api/vault` waits at most 2 s for a sign-out on its way (`authSettled`).
- The host caps the vault ciphertext (413, `VaultTooLargeError`; `MAX_HOSTED_VAULT_CIPHERTEXT_LENGTH` must not exceed the server's `MAX_VAULT_CIPHERTEXT_LENGTH`). Saves show `vaultTooLarge`; device → hosted checks the sealed size before creating anything.
- Email sign-up: the account exists before the 6-digit code. Until the diary opens, the sign-up (phrase, email, wrapped kit, `confirmed`) is kept by a `PendingSignupStore` (`lib/client/pending-signup.ts`): Android seals it in Keystore (`files/pending-signup.bin`, key `ciclo-pending-signup-v1`), the web keeps it in sessionStorage only, never localStorage. A start with no kept phrase resumes it (welcome screen card, onboarding opens on the code). Once the code is taken (`confirmed`) a failure to open the diary is `SignupConfirmedError`, and trying again never asks for a code; a resend answered `pending: false` means an earlier code went through. Any successful diary open (every `hydrate`), a device diary, a device wipe, and sign-out drop it; Android seals it under a new alias each time (like the device phrase).
- Sign-out works offline: it deletes the cached kits and last email, a pending sign-up, the kept phrase (throws if it may remain, and nothing else changes), the offline copy and the diary in memory, then calls `/api/auth/logout` without waiting. A logout that cannot reach the host: in the Android app it clears the session cookie in the app's own cookie jar (`clearSessionCookie`, the store CapacitorHttp uses); on the web it sets `ciclo.logoutPending`, says so on the welcome screen (`sessionEndPending`), and `retryPendingLogout` clears the cookie at the next start or `online`. A later sign-in replaces the cookie and clears the mark.
- Auth challenges: up to 5 live per key (two tabs or StrictMode can sign in at once). `verify` consumes the exact challenge with `DELETE … RETURNING`, so it is single use.
- Vault concurrency: `accounts.vault_version` (0005). `PUT /api/vault` is a compare-and-set on `baseVersion` (`lib/server/vault.ts`); a stale base gets 409 with the current blob, and a save without `baseVersion` gets 400. Only `GET /api/vault` reads the blob; `requireAccount` selects the id alone (its account check reads the session only). The client keeps `syncedRef` (diary + version last seen on the server), serializes saves, and on 409 decrypts the remote blob and runs `mergeDiaryEdits(base, local, remote)` (the loop is `saveWithMerge` in `lib/client/vault-sync.ts`; work started for one session never touches the next, `sessionGenRef`). When the app returns to the front or comes back online it fetches the hosted vault and replaces the diary in memory only under `shouldApplyRefresh` (newer version, no save queued or in flight, no `aria-modal` sheet open); otherwise the next save's 409 merges it (`lib/diary-merge.ts`: per day field, symptom, custom symptom, and setting; local wins only where it changed; deletions stick; period starts re-derived from merged days). Never send a full diary without a base version from new code, and never merge with the union-style `mergeDiaries` (that is for import and resurrects deletions). The CAS also refuses a save with an older `schemaVersion` than the stored one (see "Old builds and newer diaries"). `DELETE /api/account?baseVersion=N` deletes only at that vault version (409 `code: "vault-changed"` otherwise); without it the delete is unconditional. An account already deleted (a second request for the same delete) answers 404, never 409: the app removes its own copy on a 409.
- Abuse limits: `lib/server/rate-limit.ts` (`rate_limit_hits`, 0006, `RATE_LIMITS`) counts requests per key: HMAC(client IP) by default (an IPv6 address counts as its /64, `ipLimitSubject`; IPv4 as is), `limitKey("account" | "email", …)` (a keyed hash, never the raw account id or email lookup) for per-account and per-address budgets, `GLOBAL_KEY` for host-wide ones. Never store raw IPs, ids or lookups there. `takeRateLimits` is atomic and all or nothing (a transaction with `pg_advisory_xact_lock(hashtext(key))` for every key, in hash order, then one statement that counts every bucket and inserts every hit only if none is full; it must stay a separate statement after the locks so its snapshot sees what the previous holder committed; 3 round trips whatever the number of buckets; no schema change). A refusal by a bucket marked `alert` logs `RATE_LIMIT_REFUSED <bucket>` (never the key), to alert on. Buckets: `auth-challenge`, `auth-verify` (before any signature check), `account-create` (100/day) + `account-create-burst` (20/10 min), only when verify creates an account; `pool-contribute`; `recovery-fetch` (per IP only: no per-email limit, which anyone knowing an address could use to lock its owner out); code mails `recovery-register` (IP), `code-send-account`, `code-send-email` (3/hour) + `code-send-email-day` (6/day; with 5 attempts per code this bounds guessing for one address, such as an operator address not registered yet), `code-send-global` (1000/hour, a spend cap far above real sign-ups; it counts taken and new addresses alike, or it would become an oracle); code guesses `recovery-confirm` (IP) + `recovery-confirm-account`; `vault-write` (600/hour per account). Limits are generous because many people share an IP. Limits on recovery routes must stay identical for taken and unknown emails (place them before branching). Nothing writes `recovery_attempts` any more (the per-address code budget is `code-send-email`); the table stays for old rows. About 1 hit in 50 prunes rate-limit hits and recovery attempts older than a day, expired auth challenges, expired `mailbox_pending` rows, and expired `friend_boxes`; never prune accounts, vaults, mailboxes, activity days, friend books, or research rows. Friends buckets: per account `friends-book-write`, `friends-box-write` (hour) + `friends-box-write-day`, `friends-box-read`, and for a new box address `friends-box-create` (60/day); host-wide (2000 new boxes a day) `friends-box-write-global` and `friends-box-create-global` (alert). The friend-box prune runs only with `FRIENDS_AVAILABLE` and catches its own error: production may not have 0008 yet, and the cleanup rides on sign-ins and vault saves. Payload caps: vault 512 KB of ciphertext (`MAX_VAULT_CIPHERTEXT_LENGTH`), initial vault 64 KB (`MAX_INITIAL_VAULT_CIPHERTEXT_LENGTH`), vault nonce 64 chars, schemaVersion 1–1000, signature exactly 128 hex chars, recovery kit validated by `parseMailboxKit` (base64 sizes, PBKDF2-SHA-256 with 100k–10M iterations).
- API routes (`lib/server/http.ts`): every handler is wrapped in `apiRoute` (an unexpected error answers 500 and logs only error names and codes, `describeError`: drizzle's messages hold the SQL parameters, so never log an error object or message). Every route that takes a body reads it with `readJson`: 415 without `Content-Type: application/json`, 413 over the size cap (by Content-Length, and while reading the stream for a body sent without one), 400 for malformed JSON or a non-object. Requests without a body (logout, `DELETE /api/account?baseVersion=N`) need no Content-Type. Every client call with a JSON body must send that header (`apiFetch` passes it through to the app's native HTTP).
- localStorage keys migrated `oddy.*` → `ciclo.*` in `storage-migrate.ts`. Keep that one-way migrate.

## Friends

Opt-in sharing of the current cycle phase with close friends, on since 2026-11-20 and shown as experimental (a pill beside the screen title and a line in the settings sheet, `friendsExperimental*` strings). `FRIENDS_AVAILABLE` (`lib/features.ts`) gates it: false hides the screen and tab, every `/api/friends` route answers 404 (`friendsUnavailable`), and the policy's Friends parts, the `/delete-account` line and the Help article go with it (`policy.test.ts` checks the policy).

- The host can read neither what is shared nor, at rest, who is friends with whom. Keys (HKDF-SHA-256, AES-256-GCM, WebCrypto ECDH P-256; `lib/friends/crypto.ts`): S, a random secret in the invite link's fragment (`/friends/join#v1.<S>`, `lib/friends/invite.ts`); key pair A made for the invite (private half only in the inviter's sealed book, public half in the invite box); key pair B made by the joiner (public half in the handshake box, private half used once); the pair key is K = HKDF(S ‖ ECDH(A, B)). The link opens only boxes holding public keys, so reading with it never yields K: never put a secret in the invite or handshake box. The link also carries `keyFingerprint(A_pub)` (code `v1.<S>.<F>`), the joiner refuses an invite box whose key does not match, and the invite box's write token comes from A's private half (`inviteAddress(S, privateKey)`), never from S. Labels are part of the format; never change them.
- `friend_boxes` (0008): sealed messages addressed by SHA-256 of an id only two devices can derive, replaced or deleted only with the write token whose SHA-256 is stored (`putBox`, `deleteBoxes` in `lib/server/friends.ts`). Every ciphertext is the same length (`BOX_CIPHERTEXT_LENGTH`, a CHECK in SQL), `expires_at` is rounded up to a week (`BOX_TTL_DAYS` + 7 must stay within the policy's 7 weeks, `MAX_BOX_LIFE_DAYS`), and there is no account column and no write time. Never add an account column, a write time, or a join table to accounts (same rule as `research_contributions`). Known residual: the per-account `rate_limit_hits` row written just before a box write lets a database copy taken within about a day link that box to its writer (never its reader); the policy and the threat model say so. Reads are a POST so ids never sit in a URL.
- The handshake box's token comes from K, so only the joiner who made B can replace it; it stays until it expires, so a reused link gets 409. `putBox` replaces a box only with the token it was created with, expired or not: another token never takes over an address until the cleanup removed the row. The joiner refuses an invite 7 days old or more (its `at` is the creation day, kept when the box is written again); the inviter completes any answer written within 7 days of creation, whenever it sees it, and writes "ended" to a later one. A joiner still waiting after invite + handshake life gives up (ended). Order matters (`lib/client/friends-sync.ts` header): the book is saved before a box that depends on it is written, and a box is deleted only once the book no longer needs it. Removing a friend, revoking an invite and turning Friends off change the book first (turning off reads the host's book first); every refresh reads the host's book; after its writes `publishStatus` reads the book again and writes "ended" again to any friend removed meanwhile; an invite box is written again only after a fresh read of the book.
- A friend's `selfId` is pinned when the friendship starts (invite or handshake); a status with another `selfId` is ignored. Never merge or drop entries automatically on a `selfId` (the other side declares it): two cards for one person stay until the person removes one. A friend whose last status said "ended" is kept with `state: "ended"` and never written to.
- `friend_books` (0008): one sealed blob per account (`lib/friends/book.ts`), sealed with the wallet's `friendsKey` (HKDF label `ciclo-friends-v1`, `lib/crypto/wallet.ts`), compare-and-set on `version` like the vault, `ON DELETE CASCADE`. Kept apart from the diary on purpose: pair keys must never reach a diary export, and the diary schema version stays. A book of a newer format throws `NewerFriendBookError` (open read-only, never save back).
- A status (`lib/friends/payload.ts`) carries the current cycle as start, expected next start and bleed length, built from `cycleOverview`; the viewer's device turns it into a phase with `cycleTimeline` for its own date. Never send symptoms, diary notes, flow or past cycles. A pregnancy she chose to share replaces the cycle with its due date (see "Pregnancy"). With the forecast off only bleeding logged today is sent. After the expected start the card says "period expected about now" for a few days, never "days late".
- Delete routes (`/api/friends/book/delete`, `/api/friends/boxes/delete`) skip `rejectOutdatedClient`: leaving must always work. Deleting an account cascades the book; boxes have no account, so the device tells friends and deletes what it can first (`turnOffFriends`), and the rest expires.
- Not offered for an on-device diary ("Only on this device" means nothing leaves the phone).
- Screen layout (`app/friends/page.tsx`): the header has the title, refresh and settings (the sheet); then the person's note with "How friends see me" (`OwnCardPreview`: their own card from the same `buildStatus` as publishing; it sends and saves nothing), the friends' cards (the ring with the phase's icon in its middle, a tint in the phase's colour, "logged today" for bleeding logged today and otherwise when the period is expected; the line under the cards is what says phases are estimates, so keep it; when a card appears its ring turns in and fills, one card after another, and a light moves behind it, `FriendAura`: by its place in the list each card starts its loops elsewhere, at its own pace, every other one the other way, so the cards never pulse in step; transforms and opacity only, on layers blurred once), and two buttons, invite and join (`InviteCard`). The screen follows a design the owner chose (2026-11-20, "A · Pulida"): change its layout or wording only when asked. "Invite" shows the link still waiting (`liveInvites`, `lib/friends/book.ts`) and creates one only when none waits; only "New link" adds another. Never create an invite just because the card opened: five taps would fill the book. The waiting links stay reachable from the screen itself (the line under the buttons), so a full book can always be emptied.
- Provider: `FriendsProvider` (`components/friends/friends-provider.tsx`, in both root layouts) runs every change through one queue and publishes the status when what friends would get changes: at once after a change on the Friends screen, after a random 20–80 s wait after a diary change (so the write does not sit next to the vault save). A device that has seen Friends on (`ciclo.friends.<pubkeyHash>` = "on") loads it at start; others when the screen opens. The context gives it `friendsRun` (calls through `liveSessionRetry`); `wipe` and the hosted → device move call `leaveFriends` before the account delete. The tab bar takes 4 or 5 tabs (literal `grid-cols-4/5` and `w-1/4`/`w-1/5`; 10 px labels with 5). The privacy policy's Friends parts, `/delete-account`'s line and the Help article `friends` appear only with the flag on.
- Production: `0008_friends.sql` applied 2026-11-20 (snapshot first). The policy's Friends text still needs the legal read that the whole policy needs before the Play launch.

## Pregnancy

Pregnancy mode (PLAN 4, phase 3a): `PREGNANCY_AVAILABLE` (`lib/features.ts`), on since 2026-11-23. Turned off, nothing offers to turn it on (Settings, the expected-period card, a positive test in the day sheet) and `/help/pregnancy` is a 404; a diary that already holds a pregnancy still shows its card and can end it. `/dev-pregnancy` (404 in production) shows every card and sheet. Patterns while a pregnancy goes on is phase 3b (below); its week-by-week texts sit behind `PREGNANCY_WEEKS_AVAILABLE`, on since 2026-11-23 at the owner's request, with no medical review yet.
- Data: diary v7 `pregnancies` (`lib/pregnancy/record.ts`, inside a `diary-format` block that `diary-schema.test.ts` hashes): id, dating (what she entered), due date (the reference), end `{date, outcome: birth | ended}`, hidden, `friendsMode` (`noNews` | `simulated`), `bleedAnswers`. The record holds nothing about the baby; a day can hold that she felt movement (`babyMovement`, a plain daily mark of the Pregnancy group, never a count). The reason a pregnancy ended is never asked or stored. No server, route, table or pool change. JSON export includes pregnancies; CSV does not. A JSON import adds the ones the diary lacks by id only when she ticks it (`previewImport` counts them, `mergeDiaries(..., { pregnancies })`; ticked by default only into an empty diary, `importsPregnanciesByDefault`): nothing remembers a deleted pregnancy, so an old backup would bring it back. Merge is per id and field; a deletion on either device wins. Only one pregnancy goes on at a time: `startPregnancy` refuses a second one, the merge keeps this device's when two devices each started one (`onePregnancyGoingOn`, lib/diary-merge.ts), and an import never adds a second. `startPregnancy` and `changeDating` change nothing for a dating `sanitizePregnancy` would drop; the start sheet uses the same limits (ultrasound age at most `MAX_SCAN_AGE_DAYS`).
- Period starts: `derivePeriodStarts(days, pregnancies)` never starts a period from bleeding on or after a pregnancy's estimated conception day (due − 266) while it goes on, nor within 20 days of its end (42 after a birth or an end from 14+0), nor a later bleed she answered "not yet" for. Turning the mode on or off recomputes them (`withPregnancies`). The day sheet's bleeding hint follows the same day (`bleedContext`): bleeding between the last period and the conception day is her last period.
- Cycles: `lib/cycle/segments.ts` is the one place that says which intervals are cycles. The one that held a pregnancy is not (forecast, averages, Patterns rows, the research pool). While a pregnancy goes on, and after its end until a period start, there is no forecast and no phase (`insidePregnancy`), never "late". After a loss the forecast reuses earlier cycles with the Laplace scale floored at 3 days for 3 cycles; after a birth it leaves out every earlier cycle (prior only). Both are documented assumptions (docs/modeling.md). Anything that walks period starts must go through `cycleSegments`: the calendar's ovulation marks (`estimatedOvulationDates` takes the pregnancies) and Patterns (`openCycleStart`, lib/patterns/stats.ts: no open cycle, so no "now" row and no recurring-symptom window, while a pregnancy goes on or before the period comes back; `presence` uses each cycle's own end) do.
- Patterns (`components/patterns/pregnancy-patterns.tsx`, lazy-loaded by `PatternsContent`): while a pregnancy goes on the screen is about it, in a layout the owner asked for (2026-11-23; five mock-ups, a week-by-week view with a "coming up" list): the week and trimester (the card's own strings), a week chooser, "the baby" (typical size with a small chart, development facts) and "your body" for the chosen week, what she logged week by week (`pregnancySymptomWeeks`, lib/pregnancy/patterns.ts: symptoms only, the Pregnancy group included, never sex, tests or pills; baby movement apart, `babyMovementLog`), what usually comes next with dates from the due date (`MILESTONES`), when to call, and the usual Patterns cards folded under "Your cycles before the pregnancy". The texts are ES/EN content (`lib/pregnancy/guide.ts`, `guide-weeks.ts`; `contentLocale`, with the "English only for now" badge), with `GUIDE_SOURCES` listed on the screen: sizes only from growth standards (INTERGROWTH-21st crown–rump length, WHO fetal weight), weeks counted from zero like the card (a source's "week 15" is week 14 here), care windows worded "usually" / "in some countries". Never fruit comparisons, nothing celebrating, no advice for one person. Past 42 weeks with no end it stops counting, like the card. With no open cycle (a pregnancy going on, or ended and no period back yet: `pregnancyStatus`) Patterns draws no forecast card at all. `insidePregnancy` also covers the days from an end that came before the estimated conception day (a pregnancy dated from a recent period and ended within days).
- Friends: a pregnancy is private unless she chose to share it (`lib/pregnancy/friends.ts`). Private: `noNews` builds the status of the same diary without its pregnancies, byte for byte, so turning the mode on publishes nothing (publishing waits for a change); `simulated` sends her usual cycle rolled forward from her last real period, never "logged today". Shared (the owner's request, 2026-11-23): the friend book holds the id of the pregnancy she shares (`FriendBook.pregnancy`; not in the diary, so the diary schema version stays and a build from before it drops the field when it saves the book, which stops the sharing). While that pregnancy goes on and is under 42 weeks (`sharedPregnancy`), the status carries `pregnancy: { due }` in place of a cycle and nothing else about it; a friend's card shows the week counted from zero and the trimester on its own date (`readStatus` kind `pregnancy`), never the due date. It is off by default and never suggested: she turns it on in the start sheet's friends step, Settings → Pregnancy, or the Friends settings sheet. Logging the end, deleting the pregnancy, a pause, or turning it off sends the private status again, with nothing about what happened; another pregnancy is never shared without asking again. A viewer on an older build reads such a status as "no estimate". `lib/pregnancy/friends.test.ts` holds the leak list (PLAN 4.8) and the sharing rules; keep it passing.
- Pregnancy symptoms (diary v8): the symptom category `pregnancy` (`isPregnancyEntry`, `lib/symptoms/catalog.ts`) holds 12 built-ins: baby movement, heartburn, vomiting, peeing more often, swelling, Braxton Hicks, pelvic pain, leg cramps, short of breath, dizziness, food aversions, sensitive to smells. Offered only on days inside a pregnancy (`pregnancyDay`, lib/pregnancy/view.ts: from the estimated conception day, the one going on or an ended one kept and not hidden; not `insidePregnancy`). There the day sheet's chips lead with `PREGNANCY_LEAD_IDS` (`pregnancyQuickCatalog`; baby movement from 16 weeks, `MOVEMENTS_FROM_DAYS`, and only while it goes on), then favourites, then what is logged; "More symptoms" (`pickerCatalog`) shows the group first and leaves out ovulation tests and oral contraceptives unless logged that day. Elsewhere the group is not offered, but a logged entry always shows. No favourite star on the group; `toggleFavoriteSymptom` keeps favourites a filtered catalog does not list. While the pregnancy goes on, one line under the lead chips says logging alerts no one and to call straight away if the baby moves less; it opens `PREGNANCY_CALL_COPY` (lib/pregnancy/call-copy.ts, the #75 text, which guide.ts spreads back in so the guide stays lazy) in place. Never on days of an ended pregnancy. No kick counter and no "moving less" chip (a logged chip could read as handled): the owner's decisions of 2026-11-26. The group never enters `recurringSymptoms` (ordinary Patterns, tips); pregnancy Patterns counts it in `pregnancySymptomWeeks` except baby movement, which gets its own line (`babyMovementLog`: first day and its week, days per week, "only what you logged"). `deletePregnancy` strips the group's entries from its days (unless another kept pregnancy covers the day). Nothing of it reaches friends.
- Sheets (`components/pregnancy/`): every save goes through `PregnancyFlowsProvider.save` or a `.then` with `saveErrorMessage` (lib/client/save-error.ts); a save that fails shows why and the sheet stays open, never a bare `void persistDiary(...)`. The end is saved by a button that says Save; an end already logged can be corrected (Settings, `openEnd` on an ended record: `endPregnancy` again keeps her bleed answers) or taken back (`reopenPregnancy`, refused while another one goes on). Dates of a pregnancy over by now (`alreadyOver`, more than 44 weeks) are not an error: the start sheet hands them to the end sheet and `addPastPregnancy` saves both at once, so it never goes on. The sheets take Escape in the capture phase (one Back never closes the sheet and the day sheet under it; the confirmation dialog still answers first) and in the Android app Back goes back a step before closing (`onBack`); `useBackStep` does nothing under an `aria-modal` sheet.
- Wording: nothing celebrates by default; never suggest a pregnancy from a late period; never write "miscarriage" or "abortion" in the interface (Learn articles may: the after-the-end card links to `/learn/after-pregnancy-ends`, `AFTER_END_ARTICLE`, with neutral words, only for an end that was not a birth; neither "you can ovulate before that first period" line, after an end or after a birth, carries a "not contraception" sentence: the owner's choice of 2026-11-23); after the end nothing counts weeks, shows the old due date, or marks anniversaries.
- Production: turned on 2026-11-23, after the owner approved every text of the mode, the after-the-end `resuming*` strings included. The privacy policy (`DIARY_CONTENTS`, `PRIVACY_POLICY_UPDATED`), the sign-up consent strings, PRIVACY.md and docs/play/privacy-checklist.md name pregnancy dates; content/help/friends.md says what friends see during a pregnancy; Help lists `/help/pregnancy` by itself. When the texts or what a pregnancy stores change, keep all of these in step. Still open: the legal read the whole policy needs before the Play launch, and the Play data safety form.

- Android Learn ships `LEARN_ARTICLES` only. Operator edits in `learn_articles` reach the app with the next release. Help is prerendered from `content/help/`.
- Every client call to `/api` goes through `apiFetch()` (`lib/client/http.ts`), never a bare `fetch`: it builds the URL with `apiUrl()`, sends `x-ciclo-client` (`android/<versionCode>` or `web`, `lib/client-version.ts`), gives up after `REQUEST_TIMEOUT_MS` (20 s, body included; the app's native HTTP has no timeout of its own; vault loads get 60 s and vault saves 20 s plus 1 s per 8 KB) with `RequestTimeoutError`, and turns a 426 into `UpdateRequiredError`. API routes call `rejectOutdatedClient(request)` (`lib/server/client-version.ts`): 426 `code: "upgrade-required"` for an Android build below `MIN_ANDROID_VERSION_CODE`, on the vault, recovery and research routes and on a sign-up (`/api/auth/verify` with a first diary). The web, builds without the header and `android/0` (a build made without `apps/mobile/version.json` baked in) are always served, and a plain sign-in (`/api/auth/challenge`, `/api/auth/verify` without a first diary), sign-out (`/api/auth/logout`) and account deletion (`DELETE /api/account`) are never refused: an outdated build keeps a fresh session, so it can always sign out and delete the account. On a 426 the app keeps an open hosted diary readable but saves nothing (`updateRequired`, `UpdateNotice` with a Google Play link, also on `/unlock`, `/onboarding` and the welcome screen); an offline copy opened because of a 426 is not shown as "offline" (no retries; `UpdateNotice` gives its date, `copySavedAt`), and sign-out and delete still work; an on-device diary, open or locked, is unaffected. `UpdateRequiredError.reason` says why ("server" 426, "diary" newer diary, "kit" newer recovery kit); sign-in forms use `updateErrorMessage` so a 426 is not said twice and the web is never sent to Google Play. The web leaves `NEXT_PUBLIC_CICLO_API_BASE` unset, so calls stay same-origin. The Android build bakes `CICLO_API_BASE`: default `http://localhost:3000` (the local stack), release builds pass the production https origin. Never default it to production.
- `CapacitorHttp` sends `fetch` through native HTTP with the app's own cookie jar, so the session cookie stays httpOnly + SameSite=Lax and the API needs no CORS. Do not add CORS headers or `SameSite=None` for the app. Capacitor `loggingBehavior` stays `"none"` in every build: the bridge would otherwise log request/response bodies (recovery emails) and plugin results (the phrase from `DeviceVault.readPhrase`) to logcat.
- No service worker, no install prompt, no installed-PWA redirect in the app (`layout.android.tsx`, `IS_ANDROID_APP`).
- Do not reimplement crypto, forecast, diary parse/merge, or vault sync in Kotlin/Java. Native code is for platform services only (Keystore, biometrics, files, share sheet).
- Manifest: `allowBackup="false"` and `data_extraction_rules.xml` exclude all app data (WebView storage can hold the phrase). Cleartext http is allowed only in the debug source set, only to localhost. Permissions: INTERNET and CAMERA (phrase QR scanner; `uses-feature` camera `required="false"`). A WebView feature that needs a device permission is silently denied unless the manifest declares it. `configChanges` lists `fontScale` and `fontWeightAdjustment` with the others: a system font size or bold text change must not recreate the activity, which reloads the page and closes a session not kept signed in. So `MainActivity.onConfigurationChanged` applies a new font scale to the WebView itself (`setTextZoom(fontScale * 100)`, what the WebView does at creation; to be checked on a device, Android 14 scales fonts non-linearly).
- WebView: the bundle needs Chrome 111 (oklch, Next 16's targets). The first thing in the Android root layout's `<head>` is `webviewGuardScript()` (`lib/webview-update-page.ts`, ES5): it reads the Chrome/Chromium major version from the user agent and, below 111, `location.replace("/webview-update.html")`; a user agent with no version stays. That page is plain HTML with an ES5 script, in every UI language: it asks to update Android System WebView (Google Play link) and never redirects by itself; on a recent WebView it only offers Try again (`/`), so nothing can loop. Do not use Capacitor's `android.minWebViewVersion` / `server.errorPath` (a test rejects them): below Android 8 Capacitor reads the Chrome / Android WebView package versions instead of the WebView in use, so a phone with Chrome disabled would get the page on every start, Huawei's WebView is compared against another setting, and `errorPath` also replaces the app on any page load error. With no WebView at all, `MainActivity` shows `no_webview_message` (`res/values*/strings.xml`) instead of crashing on a null bridge.
- Recents: on Android 13+ `MainActivity` calls `setRecentsScreenshotEnabled(false)` for every account, so Android keeps no picture of the app for the recents screen: once Ciclo has left the front, recents shows it without its content. Opening recents while Ciclo is in front still shows the live app; only `FLAG_SECURE` hides that, and it comes only with the app lock. Screenshots stay allowed without the lock.
- Clipboard: copying the phrase (onboarding) goes through `copyPhrase` (`lib/client/phrase-clipboard.ts`). In the app `DeviceVault.copySensitive` marks the clip sensitive (Android 13+ hides it in the preview); about 60 s later `clearCopied` empties the clipboard if the clip is still Ciclo's (by its label). Android 10+ lets only the app in front read the clipboard: `clearCopied` then answers `checked: false` and `phraseCopier` tries again each time the app comes back into view, until it could look. The web clears it only with read permission already granted, or when the page kept the focus and saw no copy. Phrase and password fields never autocapitalise, autocorrect or spellcheck (`PasswordInput`).
- Local run: `docker compose up -d db mailpit`, `cd apps/web && npm run dev`, `adb reverse tcp:3000 tcp:3000`, then `cd apps/mobile && npm run build && npm run android`. Gradle 8.14 (Capacitor template) needs JDK 21; Android Studio's bundled JBR 25 cannot run it. CLI builds also need `ANDROID_HOME`.
- On-device mode ("Only on this device", Android only): `ciclo-context.tsx` loads/saves through a `VaultBackend` (`hostedVault` in `lib/client/api.ts`, device backend in `lib/device-vault.ts`). Both keep compare-and-set; never bypass `saveMerged`. The device file is the same sealed blob + a version; a damaged file must throw (`UnreadableDeviceDiaryError`), never read as empty, and a save on top of a file that is gone (base version above 0) throws too. The phrase lives only in `files/device-phrase.bin`, sealed by an Android Keystore key (`DeviceVaultPlugin.java`), never in WebView storage. `storePhrase` seals under a new alias (`ciclo-device-phrase[-auth]-v1-<uuid>`, named in the file: phrase format 2; format 1 files use the fixed alias) and deletes the old keys only after the new file is written, so a canceled check or failed write changes nothing. `clear()` deletes the diary file first and the phrase and keys only once the diary is gone. Every sealed write (device phrase, hosted phrase, pending sign-up) counts only once the file reads back as written and names the new alias (and opens, for keys without a user check); a write that did not land drops the new key, and an uncertain one keeps every key. Load the plugin only through `import("@/lib/client/device-storage")` behind `IS_ANDROID_APP`.
- A device diary that stays locked at start says why (`deviceLockReason` from the plugin's error code: canceled, key-invalidated, no-key, key-error, unreadable); the lock screen hides what cannot work and offers `deleteLockedDeviceDiary` behind a typed word. If `status()` fails, `deviceStatusFailed` blocks every route with a retry; never read it as "no diary".
- One diary per install: while a device diary exists, `unlock()` opens that file and must never call `loginWithWallet` (the hosted account would be a different diary, and with a first diary it would create one). Never overwrite an existing device diary.
- Hosted accounts in the app: "Keep me signed in" seals the phrase with its own plain Keystore key (`ciclo-hosted-phrase-v1-<uuid>`, a new one per write like the device phrase; format 1 files use `ciclo-hosted-phrase-v1`) in `files/hosted-phrase.bin` (`storeHostedPhrase` / `readHostedPhrase` / `clearHostedPhrase`), never in WebView storage, and never as a fallback when Keystore fails. Unchecked: memory only. `androidPhraseStore.read` moves a phrase left in localStorage by older versions into Keystore and deletes the plaintext only after the sealed copy reads back. Sign-out must fail if the sealed phrase may remain; `clear()` on the device diary leaves the hosted phrase alone.
- Offline copy (hosted accounts kept signed in only): `files/hosted-diary-copy.json` (`lib/hosted-copy.ts`, `readHostedCopy` / `writeHostedCopy` / `clearHostedCopy`) holds the host's sealed blob + version + `savedAt`, rewritten after every hosted load and save (best effort). At start, if sign-in or the vault load fails for any reason but `AccountNotFoundError`, the copy opens read-only through `offlineBackend()` (save throws `OfflineError`) and the context sets `offline`. Never write a hosted diary from the copy: `persistDiary`, `moveToDevice`, `changePassword`, and `wipe` call `assertOnline` first, and the UI disables them (`OfflineNotice`, read-only day sheet); sign-out works offline. The `online` event, the app returning to the front, a growing timer, or Try again re-run `restoreStoredSession` through `retryRestore` (one at a time). `keepCopy` deletes a copy whose write landed after a sign-out. Delete the copy (`keepCopies(false)`) on sign-out, account delete, moving to the device, creating a device diary, and any sign-in without "Keep me signed in". The copy is never a device diary: `status().hasDiary` must not see it.
- Moving device ↔ hosted deletes the old copy only after the new one is saved. Device → hosted creates the account with an empty first diary (the first vault is capped at 64 KB) and saves the device diary on top, or merges it into an account that already holds entries (the device diary's settings win). Once the host has it, the hosted phrase is sealed and read back (`hostedPhraseStore.writeVerified`; a failure stops the move with nothing deleted), then the device files are deleted and the context switches to the host with the data already in hand (no network call), so a failure after that point can never leave the device backend in charge of a file that is gone; if the delete itself fails, nothing switches and the hosted phrase is cleared again, unless the device phrase is already gone (`status().hasPhrase`). Hosted → device (`lib/client/move-to-device.ts`) copies the host's latest vault (not the one in memory), then deletes the account at that version. The device files are removed again only when the host clearly refused (409, 426, other 4xx). When the answer is lost (network, timeout, 5xx) the delete may have happened or may still land, so the device copy always stays: it checks whether the account is gone, tries the delete once more (a 409 then means another device saved, nothing could be deleted, and the out-of-date device copy goes), and otherwise reports `hostedDeleted: "unconfirmed"` (Settings tells the person how to delete the server copy).
- App lock (optional, Android 11+): per-use Keystore key behind a fingerprint or screen-lock check, `FLAG_SECURE`, and locking after 30 s in the background (a timer in the background too, and the check on return). The screen is covered (`appCovered`, set with `flushSync` in the `visibilitychange` that hides the page) until the app is back within the grace time or the lock screen takes over. Turning it off reads the phrase through the same check first (`setAppLock(false)`), unless the key can never open again (`phraseKeyIsGone`: the diary is open because the 12 words were typed). On Android 7–10 Settings says it needs Android 11 (`status().lockSupported`), not "set up a fingerprint". `DeviceLockGate` covers every route but `/unlock`.
- Exports go through `saveFile()` (share sheet in the app). User Help: `android-on-device`.
- No browser password store in the WebView: `storeBrowserPassword` does nothing in the app, Settings hides the email/password "Save in the browser" form and `SavePhraseForm`, and calls that section "Your 12-word phrase" (`onboardingTitle`; the QR stays).
- Back button: `MainActivity` asks `window.cicloBack()` (`lib/client/android-back.ts`) before WebView history. Back sends Escape to an open `aria-modal="true"` overlay, so every sheet or dialog must close on Escape through a `window` keydown listener. The confirmation dialog listens in the capture phase and stops the event, so Back closes it and not the sheet under it. Screens with inner steps register `useBackStep`. Sign-in forms leave with `returnTo()` (`lib/client/back-navigation.ts`), never `router.push`, so Back does not reopen the form.

## What not to build here

- Native (Kotlin/Swift) reimplementations of the app, federated learning, custom cryptography, confirmed ovulation claims. The Android app is the Capacitor shell above.
- Using Help as a second Learn tab, or Learn as hosting docs.
- Tailscale, ngrok, or other tunnels as the documented access path.
- Deep learning “improvements” to the forecast.

## When behaviour changes

Update the matching Help article and engineering doc in the same change. If you add a Help slug, add it to `HELP_ARTICLES` and a `content/help/<slug>.md` whose first line is `# <title>` matching the catalog. Run `cd apps/web && npm test`. Forecast changes also need Python tests + parity fixtures + CONTRIBUTING benchmark rules.
