# agents.txt — OpenCiclo / Ciclo

Machine-oriented map of this repository. Humans should start at README.md, /help, and CONTRIBUTING.md.
Do not treat this file as user-facing copy. Do not paste it into the UI.

Live copy on a hosted app: GET /agents.txt (apps/web/public/agents.txt).
Cursor: also see the short AGENTS.md at the repo root. Do not edit apps/web/AGENTS.md; Next.js regenerates it.

## Product split

- OpenCiclo: Python forecasting library at repo root (`openciclo/`). Local-first. No accounts, sockets, or telemetry in the package.
- Ciclo: optional Next.js web app in `apps/web/`. Encrypted diary + TypeScript port of the released forecast path.
- Names: Python import is `openciclo`, never `oddy`. Some crypto labels and legacy cookies still say `oddy-*` / `oddy_session` — do not rename those without a migration.
- Public name in the UI: Ciclo. Repo/docs: OpenCiclo.

## Non-negotiables

- Not a medical device. Forecasts can be wrong. Not contraception, not a fertility/ovulation test, not pregnancy detection.
- User-facing copy that discusses cycles must keep that disclaimer (see `apps/web/lib/i18n.ts` `disclaimer`).
- No Clerk, Auth0, analytics SDKs, ad pixels, or exception trackers that could receive health fields.
- No neural nets / transformers / deep learning.
- Do not log period dates, mnemonics, passwords, AES keys, or plaintext diary.
- Do not add `user_id` / `account_id` / `pubkey_hash` to `research_contributions`. A join table account→pool_id is a de-anonymization bug.
- Do not mix Utah/Creighton into `openciclo/artifacts/released_model.json`. mcPHASES aggregate prior only.
- Do not commit restricted CSVs (mcPHASES, Creighton, etc.). Gitignored under `training/dataset-do-not-commit/`.
- Do not invent metrics. Do not choose `model_id` from synthetic CI scores.
- English for code, comments, and documentation. UI strings: Spanish + English in `i18n.ts`. Help pages: English only.
- Documentation voice for humans: short sentences, define jargon once, no marketing filler. This file is exempt.

## Hosting

- Intended production: Vercel project root directory `apps/web` + Neon Postgres.
- Env: `DATABASE_URL`, `SESSION_SECRET`, `EMAIL_LOOKUP_SECRET`, `APP_URL` (no trailing slash). Email signup needs `RESEND_API_KEY` + `MAIL_FROM` (production) or SMTP (local Mailpit). If neither is set, email signup is 503. Optional `CONSOLE_EMAILS` (comma-separated). If unset, `/console` is 404. Day-to-day email sign-in does not use inbox magic links; signup sends a 6-digit code once.
- SQL: `apps/web/drizzle/0000_init.sql`, `0001_pool_upsert.sql`, `0002_learn_articles.sql`, `0003_mailbox_pending.sql`, `0004_account_activity.sql`, `0005_vault_version.sql`. No plaintext health columns. Never store plaintext email — HMAC `email_lookup` only. `0004` is one row per account per UTC day on sign-in; the console shows counts only.
- Production has real users. Migrations are hand-written SQL, additive, idempotent (`IF NOT EXISTS`), numbered with no gaps, applied with `psql -v ON_ERROR_STOP=1 -1 -f` after a Neon snapshot. `lib/db/migrations.test.ts` rejects DROP/TRUNCATE/DELETE/UPDATE/RENAME/ALTER COLUMN unless listed in `REVIEWED`, and checks every file is listed in docker-compose.yml, README.md, and the two hosting Help pages.
- Never use `drizzle-kit push` (removed from the repo). `lib/db/schema.ts` mirrors the SQL, including the partial unique index on `research_contributions.contributor_key_hash`; `schema-drift.test.ts` fails on any mismatch. Upserts on a partial index need `targetWhere` with the same predicate.
- Local UI: `cd apps/web && npm run dev` with `.env.local` from `.env.template`. You cannot see or edit `.env`.
- Local stack: `docker compose up --build` from repo root. `APP_URL` is `http://localhost:3000`. Bind is `127.0.0.1:3000`.
- Do not document or reintroduce Tailscale / serve tunnels. Public access is Vercel.
- Docker image copies `content/` into the runner so `/help` can `readFileSync` markdown (also `outputFileTracingIncludes` in `next.config.ts`).
- `/dev-seasons` is a playground; `notFound()` in production. Hide tab bar on `/dev-*`, `/help`, and `/console`.
- Next CSP: relax `unsafe-eval` + `ws:` only when `NODE_ENV !== production`.

## Python library map

```
openciclo.schemas          Pydantic models
openciclo.data             cycle math, validation, synthetic, mcPHASES/Creighton loaders
openciclo.features         recency weights, length summaries
openciclo.models           baselines, shrinkage, population prior
openciclo.artifacts        released_model.json (mcPHASES aggregate; no microdata)
openciclo.forecasting      public predict()
openciclo.explanations     drivers (contributed to prediction, not causation)
openciclo.evaluation       walk-forward; CI synthetic; mcphases --fit-release
openciclo.calibration      reliability summaries
```

Public API: `from openciclo import predict`. Docs: `docs/api.md`.
Parity vectors: `python scripts/generate_forecast_parity.py` → `tests/fixtures/forecast_parity.json`.
Tests: `pytest`, `ruff`, `mypy openciclo`.

Walk-forward: only starts before s_k may forecast s_k. Never shuffle a person’s cycles into random train/test.

Shrinkage (released default): mix personal median with population prior; k from the release artifact (web port uses k=2, discrete Laplace 1–90). Cold start (0–1 starts) → prior, high uncertainty.

V1 predicts next period start and cycle length only. Optional observations are ignored by V0 predictors.

Diary schema currently v6: period starts, daily flow/mucus/symptoms/notes, forecastingEnabled. Migrations in parseDiary. New fields go in the encrypted blob, not new Postgres health columns.

Phase heuristic (`phaseAtDate` / `cycleOverview`): flow today → menstrual observed; else calendar windows from last start + expected bleed length + ovulation window 16–10 days before next start. Independent of `predict()`. If forecastingEnabled is false, do not show estimated follicular/ovulation/luteal.

Inner seasons: winter=menstrual, spring=follicular, summer=ovulation, fall=luteal. Overlay: `season-guide-overlay.tsx`. Setting: visualSeasons. Hidden for now: `VISUAL_SEASONS_AVAILABLE` is false, so the Settings switch is hidden and the context reports visualSeasons=false even if `ciclo.visualSeasons` is "true". Keep the stored value; flip the flag to bring it back.

Tab bar: every tab change, tapped or dragged, is a real `router.push` (Android Back walks WebView history). Screens slide as a carousel through React `<ViewTransition>` in `AppShell` (class `tab-slide`, CSS in `globals.css`). The tab bar sets `data-tab-slide` on `<html>` in the commit that swaps screens; AppShell's `onEnter` skips the arriving screen's entrance animations (fade-up) while it slides. While the selection is dragged, the screen on display (registered by AppShell in `lib/client/tab-screen.ts`) moves with it, and each tab it snaps to is pushed with the finger still down (a fast sweep across several tabs pushes once, where the finger stops); `data-tab-drag` and `--tab-slide-out` / `--tab-slide-in` make that slide start where the drag left both screens and end with a spring. React renders a popstate synchronously with no view transition, so Back keeps the fade-up. Respect `prefers-reduced-motion`. No swipe on screen content; only the tab bar drags.

Intermenstrual bleeding is a symptom, never a period start.

## Crypto / identity (do not “simplify”)

- Device generates BIP39 12-word mnemonic.
- HKDF-SHA-256 info labels are `oddy-aes-v1` and `oddy-sign-v1` in `wallet.ts`. Changing them breaks existing vaults.
- AES-256-GCM for diary. Ed25519 for login challenge signatures.
- Email path: password wraps mnemonic (PBKDF2-SHA-256 + AES-GCM). Server stores HMAC(email) + wrapped kit only after a 6-digit inbox code (`mailbox_pending` then `recovery_mailboxes.verified_at`). Plaintext email is never a Postgres column. `POST /api/recovery/fetch` returns ciphertext only for verified mailboxes. Server must never unwrap.
- Only `/api/recovery/register` sends mail, so only it checks the address shape: `parseMailboxEmail` (`lib/server/mailbox.ts`) keeps the HMAC normalization (trim, lowercase) and rejects whitespace, control characters, comments, angle brackets, quotes, groups, lists, and anything over 254 characters with a 400 before any lookup. Do not add that check to `/api/recovery/fetch`: a mailbox registered before it existed would be locked out.
- Never reveal whether an email has an account. `/api/recovery/fetch` answers unknown and unverified emails with a decoy kit (`lib/server/recovery-decoy.ts`: deterministic per email, same fields, sizes, and `wrapParams` key order as a real kit read from jsonb); never return 404. `/api/recovery/register` treats "taken by another account" like a new email: same 429 accounting, `{ pending: true }`, and `MAILBOX_PENDING_MIN_RESPONSE_MS` floor; the code mail goes out in `after()`. Client errors stay generic ("wrong email or password"); only 429 has its own message. Do not use `recovery_tokens` (that would look like a password reset).
- No host-side password reset (magic link / email alone). The signup code authorizes inserting the already-wrapped kit; it does not unwrap. Changing the wrap password while unlocked is allowed: re-wrap the mnemonic (own verified mailbox, no new code); do not rotate AES or re-encrypt the diary. Lost password + lost phrase ⇒ lost hosted diary. Export/import restores data, not the old key.
- Deleting the account row cascades `recovery_mailboxes` and `mailbox_pending` (`ON DELETE CASCADE`), so that HMAC is free for someone else to verify.
- Session cookie; legacy name `oddy_session` still recognized. Optional persist unlock writes `ciclo.mnemonic` to localStorage; otherwise sessionStorage only. Never send the mnemonic to the server.
- Startup restore (`restoreStoredSession` in `ciclo-context.tsx`) forgets the stored mnemonic only if it is invalid. Network, server, or sign-in failures keep it and show Try again (`restoreFailed`). `hydrate` sets the wallet only after the vault is fetched and decrypted; never expose an unlocked wallet next to a placeholder diary, because the next save would upload it over the real vault. `fetchVault` throws on 401/404.
- Auth challenges: up to 5 live per key (two tabs or StrictMode can sign in at once). `verify` consumes the exact challenge with `DELETE … RETURNING`, so it is single use.
- Vault concurrency: `accounts.vault_version` (0005). `PUT /api/vault` with `baseVersion` is a compare-and-set (`lib/server/vault.ts`); a stale base gets 409 with the current blob. Without `baseVersion` (pre-0005 clients) the write is unconditional but still bumps the version. The client keeps `syncedRef` (diary + version last seen on the server), serializes saves, and on 409 decrypts the remote blob and runs `mergeDiaryEdits(base, local, remote)` (`lib/diary-merge.ts`: per day field, symptom, custom symptom, and setting; local wins only where it changed; deletions stick; period starts re-derived from merged days). Never send a full diary without a base version from new code, and never merge with the union-style `mergeDiaries` (that is for import and resurrects deletions).
- localStorage keys migrated `oddy.*` → `ciclo.*` in `storage-migrate.ts`. Keep that one-way migrate.

## Research pool

POST integer cycle lengths, no pubkey. Server assigns opaque pool_id. Device remembers “already contributed”. Training on this pool is out of scope until explicitly designed. UI must warn that uploaded rows cannot be deleted by account.

## Operator console

- Route `/console`. Not linked from marketing or the tab bar. `robots: noindex`.
- Gate: `CONSOLE_EMAILS`. Compare HMAC(email) to `recovery_mailboxes.email_lookup` for the session account where `verified_at` is set. Never store or log plaintext operator emails in the panel.
- Phrase-only accounts cannot match the allowlist.
- Stats are row counts and timestamps only. Sign-in writes `account_activity_days` (account id + UTC day) so the console can count unique opens. Verified mailboxes whose HMAC is in `CONSOLE_EMAILS` are not counted. Do not list those rows, `pubkey_hash`, emails, ciphertext, or `cycle_lengths`. Do not join research rows to accounts.
- Learn CMS writes `learn_articles`. Deleting a DB row restores the shipped article if that slug exists in `LEARN_ARTICLES`.

## What not to build here

- Native mobile apps, federated learning, custom cryptography, confirmed ovulation claims.
- Using Help as a second Learn tab, or Learn as hosting docs.
- Tailscale, ngrok, or other tunnels as the documented access path.
- Deep learning “improvements” to the forecast.

## When behaviour changes

Update the matching Help article and engineering doc in the same change. If you add a Help slug, add it to `HELP_ARTICLES` and a `content/help/<slug>.md` whose first line is `# <title>` matching the catalog. Run `cd apps/web && npm test`. Forecast changes also need Python tests + parity fixtures + CONTRIBUTING benchmark rules.
